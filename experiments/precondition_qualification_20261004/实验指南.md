# 实验指南：先做资格检查，再决定是否学习操作前提

2026-10-04。适用：Windows PowerShell 或其他 Python 3.10+ 环境。以下所有命令在本目录执行。依赖仅为 Python 标准库。

**本轮交付目标不是新模型或新 benchmark，而是：两类有证据的真实事故、8 个动作前状态、A/B/C 共 48 次判定、一张有来源的继续/停止决定表。** 实际事故材料仍需你从本机原始记录补齐；目录里没有冒充真实事故的合成标签。同步代码不授权自动花费，不续用旧批次的无限预算。

## 0. 阶段与放行条件

| 阶段 | 产物 | 通过条件 | 不能推出 |
|---|---|---|---|
| Q0 离线代码验收 | probe 结果、14 项测试 | SQL/反例检查、模板拒绝、账本与 mock 流程通过 | 模型有效、provider 可用 |
| Q1 事故资格 | 五个数据/签认文件 | 两个独立机制、合法可见证据、正确且可检查的真值、合法近邻 | 记忆必然有用 |
| Q2 请求与接口 | 48 个冻结请求、人工审核；最多一次独立 smoke | 无泄漏、组间输入正确、真实服务格式/usage 可核验 | 研究方向有效 |
| Q3 简单对照 | A/B/C、每状态两次、逐请求原始证据 | 完整性和费用口径可核查，按预登记规则分析 | 统计显著、执行层成功 |
| Q4 决策 | `资格检查结果.md` 补完人工结论 | 停止/修数据/采用简单方案/有限端到端/成本假设之一 | 自动开始下一阶段 |

不要把 Q0 的“测试通过”或 Q2 的“接口通过”，填写成 Q4 的研究 GO。

## 2. Q1：如何准备两类事故

### 2.1 最低证据

每类至少有一次真实失败和有效修复。保存可追溯的文件/会话 ID、消息或行范围，明确哪些内容在当时动作前可见，哪些是后来才知道。真实原始材料缺失时，复盘只能当素材，不能把事后描述伪造成原始状态。

每类准备四种状态：重复同类错误、前提满足的正常情况、动作相似但目标不同的合法近邻、作用域或明确规则变化。控制变体必须标明是基于真实事故构造的，不伪称自然发生率。两个项目名不同、实际都是关联重复计数，不算两个独立机制。

优先找有可恢复环境、能用程序或外部证据核验结果的事故。不要在真实数据库、真实凭据或不可逆文件上试错。凭据案例使用假值和模拟账户；已知启动限制可能直接写成工程检查，并不自动支撑学习必要性。

### 2.2 五个文件分别放什么

| 文件 | 模型能否看到 | 你需要填写 |
|---|---|---|
| `public_cases.jsonl` | 每次只看到对应当前案例 | `case_id`、当前任务 `task`、动作前合法状态 `current_state`、待执行动作 `proposed_action` |
| `history.json` | B/C 看到同一份全部历史，A 不看 | 两类事故的合法历史动作、观察、反馈、修复；不能含本轮目标答案/未来变体的执行结果 |
| `evaluator_cases.jsonl` | 不发送 | 案例所属机制、变体类型、各组真值、外部证据和判定理由 |
| `incidents.json` | 不发送 | 来源、真实事故、修复、合法例外、当前信息充分性、已有简单修复、评分器核验 |
| `review.json` | 不发送 | 人工资格审查、预登记决策标准与成本范围 |

保持 8 个 `q001`–`q008` 样式的不透明 ID，不在 ID 中写 `unsafe`、`duplicate_error` 等标签。公共案例顶层只能有模板中的四个字段；`current_state` 可以是文字或 JSON。历史是自然可见证据，不要人工代写“正确规则”，除非原用户当时真的明确说过。

两类事故在此 pilot 中必须属于允许共同访问的同一研究语料范围。不应把不同私有用户的记录拼在一起。若实际需逐项目权限过滤，应先共同实现并冻结，不在这一轮暗中给 B/C 额外授权。

`evaluator_cases.jsonl` 的一行示意如下，**只是格式，不是一个可直接运行的真实案例**：

```json
{"case":{"case_id":"q001"},"family_id":"f1","variant":"recurrence","expected_by_arm":{"current":"inspect","history":"block","preflight":"block"},"decision_basis":"填写规范、实际状态和独立核验如何支持该结论","evidence_refs":["填写原始证据范围"]}
```

每类四个 `variant` 固定为 `recurrence`、`normal`、`legitimate_neighbor`、`scope_change`，各一次。B/C 必须有 allow 和 block 两类。

### 2.3 特别处理“当前组不知道”的情况

如果 A 没有历史就确实无法决定，它的正确判定可以是 `inspect`，不强迫猜隐藏规则。若当前资料已足够，就按真实 allow/block 标注。B/C 的证据相同，真值必须相同。

首批只选 B/C 信息充分、能决定 allow/block 的状态。仍有歧义的状态单列，不强塞二元标签。未来测试有工具的查证过程时，另行定义 inspect 后的合法行为。

**`inspect` 即使判定合适，也不表示业务完成。** `matched_decision` 是符合该组信息条件的判定，不可简单拿 A/B/C 总匹配数相减充当任务质量增益。应逐题结合信息充分性，区分“需要历史”“本题执行错误”和“合理待核验”。

### 2.4 评分器和人工签认

至少验证：合法动作被允许；原错误被拒；空产物、关键字段/金额/状态故意改错能被发现；合法近邻不会被旧规则误拦。评价器必须调用真正候选结果，而不是参考实现覆盖候选。只用另一个模型觉得合理，不足以建立真值。

在 `incidents.json.verifier_evidence` 填写实际核验产物位置。`review.json` 的八项 checks 必须逐项完成，再填写 reviewer、reviewed_at 和 approved。脚本只检查结构和签认，**不能验证你填的来源真实、两类机制真的独立或自然语言没有泄漏**。

在 `decision_policy` 预登记如何处置 A/B/C 的结果；建议使用第 5 节的分流。进入“学习方法”至少需要：完整 C 证据下，两个独立机制各出现可定位、两次重复的适用条件问题，并通过原文复核；这只是进入下一步的保守筛查，不是统计证明。成本分支另登记可接受质量、复用次数与总成本口径，不事后改成对结果有利的标准。

```powershell
python -X utf8 qualification.py check
```

输出 `STRUCTURE_AND_ATTESTATIONS_PASS_NOT_SEMANTIC_PROOF`、8 案例、2 机制、48 计划调用及五文件哈希后，才进入 Q2。

## 3. Q2：先冻结 payload，再接真实模型

### 3.1 provider 与凭据

继续使用已有、已获授权的模型 ID 和安全凭据加载入口。不在 JSON、命令历史或 Git 文件里粘贴真实 key，不改原凭据存储方式。脚本只读取进程环境中的 `EXPERIMENT_API_KEY`，以及完整兼容 endpoint `MEMORY_GATE_ENDPOINT`。

```powershell
# 不含密钥；改为你已经确认的完整 Chat Completions HTTPS endpoint。
$env:MEMORY_GATE_ENDPOINT = 'https://YOUR_PROVIDER/COMPLETE_CHAT_COMPLETIONS_PATH'
$model = 'YOUR_EXISTING_MODEL_ID'
# 用已有安全加载器给当前进程设置 EXPERIMENT_API_KEY，不把 key 写进脚本。
```

本次没有访问你的真实凭据，也没有验证 GLM 接口。默认非流式 `max_tokens=2048`；provider 特有字段可通过 JSON `--options-file` 提供，例如你已核验的 thinking 配置。不能借 options 覆盖 model/messages/stream/n 或输出预算。需要不同协议时先改共同适配、重跑离线测试，再冻结所有组，不能只给某一组修接口。

若现有入口仍使用按 Windows 账户绑定的 DPAPI，沿用原普通账户模型进程，不为本脚本切换账户或提权。这里不需要 WSL 或新的 broker。

### 3.2 可选的一次 smoke

只在 provider 兼容性未确认时运行一个独立、非正式案例；先创建 dry-run：

```powershell
python -X utf8 model_gate.py --data outputs --case-id q000 --arm current --max-calls 1 --model $model --run-dir runs/smoke_plan
```

审核请求后，**下面这一条才会付费调用**：

```powershell
python -X utf8 model_gate.py --data outputs --case-id q000 --arm current --max-calls 1 --model $model --plan runs/smoke_plan --run-dir runs/smoke_actual --execute
```

验收 transport/返回格式/finish_reason/usage，而不是以答对 SQL 作为放行条件。查看 `manifest.json`、request/response、`results.jsonl`。接口失败应先停止，别直接消耗 48 次。smoke 是额外最多一次调用，不属于正式 48 次，也不得当研究成绩。

### 3.3 生成并人工核对 48 个正式请求

```powershell
python -X utf8 qualification.py prepare --model $model --run-dir runs/plan_v1
# 有 provider options 时在 prepare 中增加 --options-file .local/provider_options.json
```

这一步没有 HTTP。计划是 2 机制 × 4 状态 × 3 组 × 2 次 = 48。

- A/current：当前合法状态与动作；仍保留共同的基本操作判断 system 指令，不是故意弱化的无提示模型。
- B/history：A 加完整合法历史。
- C/preflight：B 加通用适用性检查；不添加真实规则或 evaluator 标签。

组内案例块按固定 seed 排列，每个“案例 × 重复”块交错 A/B/C 并轮换先后；48 次顺序执行。此安排减轻批次顺序差异，但不能消除 provider 漂移/缓存/模型随机性。两个重复不是两个独立用户。

人工检查 **全部 48 个 `*.request.json`**，确认 A 不含历史，B/C 历史相同；没有私有判定、反例类别、目标执行后反馈、key 或跨用户资料。确认模型/options/预算后，填写 `runs/plan_v1/payload_review.json` 的 approved/reviewer/reviewed_at，保留自动生成的 request_hashes。

数据、评分、签认和请求以哈希冻结。不要手改 request 来修提示；需修改源输入/代码、创建新 plan 并重新审核。模型别名不能锁权重时，在结论中保留限制。

## 4. Q3：显式执行与离线评分

```powershell
# 以下显式 --execute 才会发出模型请求；本轮上限 48 次，无自动重试。
python -X utf8 qualification.py run --plan runs/plan_v1 --run-dir runs/actual_v1 --execute
python -X utf8 qualification.py accept --run-dir runs/actual_v1
```

自定义数据路径时，上述各阶段统一加 `--data 路径`，不要中途换一套案例。

安全边界：拒绝覆盖已有目录；执行前验证数据/真值/审核未变、请求与 plan 相同；每次尝试先记 `started.jsonl`。HTTP/传输失败停止批次，格式无效保留原回复，不偷偷修复或重跑。中途崩溃的 started-without-result 列为未知尝试，不能当零成本。脚本不提供自动恢复或断点补跑，旧目录永久保留；补跑范围、理由和已发生费用须另记，不因答案差而重试。

预算边界：正式 48 调用、每次输出上限 2048、请求 UTF-8 序列化上限 65536 bytes、请求超时 180 秒；bytes 不是 tokens。没有准确输入-token、累计金额硬上限，也不承诺 token 比等于金额比。正式＋一次 smoke 最多 49 次调用，离线测试不计入付费量。若不能接受这个调用/输出/请求大小包络，应先共同修改并冻结预算，不直接启动。

产物：

| 文件 | 看什么 |
|---|---|
| `manifest.json`、`qualification.json` | 模型、顺序、界限、代码和数据/评分哈希 |
| `*.request.json`、`*.response.json` | 实际模型输入输出；响应可能含额外 provider 字段，不要未经脱敏发布 |
| `started.jsonl`、`results.jsonl`、`completion.json` | 每次尝试、状态、判定、usage、returned_model、finish_reason、耗时 |
| `score.json` | 组别与机制分项、逐题结果、重复 C 错误候选、未知费用 |
| `资格检查结果.md` | 机械摘要与待人工完成的研究分流 |

自动评分入口只用于隔离评测；它不把 evaluator 文件发给模型。目录结构和字段黑名单不是完整安全沙箱；未来给 agent 文件工具时必须把评测文件移出可访问挂载。

## 5. Q4：如何验收，而不把数字当结论

### 5.1 技术完整性

完整批次应有 48 个计划 key、48 次尝试、48 条结果，无重复/陌生 ID；payload 可核验；completion 为 completed。invalid_output、传输失败、缺失单列，不能丢掉再重算高分。技术 incomplete 时先解决接口/数据/观测，不能据此否定学习方向。

`technical_complete=true` 仅指全部响应有效并完成，不表示答对。unknown usage 即使不影响判定分析，也阻止准确全成本结论；账本中的已知 token 是小计。比较缓存、非缓存、输出的价格时再核对服务商实际口径和价格，不把零费用作为默认值。

### 5.2 行为与信息的分流

| 实际观察 | 决定 |
|---|---|
| A 已解决，B/C 无额外需求价值 | 此样本不支持记忆必要性，保留普通工程回归 |
| A 缺信息/失败，B 已解决 | 先解决经验交付，不先开发前提学习 |
| B 失败、C 已解决 | 采用通用 preflight；除非有独立成本目标，不加新方法 |
| C 信息充分，两个机制均有可复现适用条件问题 | 原文复核后，进入有限规则生成与执行检验 |
| C 判对，但原 agent 不调用/不遵守 | 修执行挂接，不称规则归纳失败 |
| C 足够正确但反复推理昂贵 | 单独提出规则编译摊销假设，比较全部构建/维护费用 |
| 真值、来源、信息充分性无法确认 | 停在 Q1，补证据而不是继续跑模型 |

复核 `repeated_preflight_nonmatches`：它含过度 inspect，不含“已确认同根因”判断。需对照原始响应和来源，说明两次是否真是相同条件错误，而非两个无关错误。inspect 本身永不算业务成功；block 只是拒绝当前动作，不代表合法业务任务已完成。

本轮可接受的结尾也包括“不值得继续”。在报告中填写判定人、引用范围、适用分母、未知项、下一阶段有限范围。无结论时写证据不足，不通过不断改数据来制造 GO。

## 6. 放行后只做有限端到端，不立刻建立完整 memory 系统

在快照副本验证：候选前提是否从自然历史提出 → 检查能否运行 → 能否取得状态 → 是否在动作前调用 → 错误操作是否真实避免 → 合法业务能否最终完成。

一次生成检查 G0 是必需强简单参照。带反例核验的 G1 必须与获得相同额外证据或近似计算预算的简单方案比较。反例真值来自独立规范/环境，不能由提出规则的模型自己出题、自己判定、宣布正确。人工特征工程要披露，不能把给定特征上的成功说成自然轨迹归纳成功。

固定一个未见的合法例外/作用范围变化；验证错误复发率和误阻断/完成率，计入生成、核验、修订、状态提取、执行、恢复费用。代码只在隔离沙箱运行，不触真实凭据或不可逆资源；学到的检查不能扩大既有授权。

更完整的边界见 [验证协议](VALIDATION_PROTOCOL_CN.md)。本工具包尚未实现这一步，也不以动作分类成绩冒充端到端结果。

## 7. 回传什么、不要上传什么

本地同步后可以直接运行 Q0 和生成模板。真实付费 Q3 必须等待 Q1/Q2 的材料与人工验收完成。

最终优先回传：脱敏后的资格结论、按组/机制汇总、少量决定性原始输入输出、全部已发生/未知费用和未完成项。`.local/`、`runs/`、`outputs/` 已被忽略；不应直接提交原始会话、私有 evaluator、密钥、密文或真实账户信息。代码与指南放在本目录，旧实验停止标记和历史报告原样保留。

# Agent、memory 与模型协议

## 固定运行载体

pi 使用官方发布的 `@earendil-works/pi-agent-core@1.0.0` 和 `pi-ai@1.0.0`，npm gitHead 为 `a13d35a742c6ef8462812a28fbe1d8c8b7431c32`。已核查 [固定版 agent-loop.ts](https://github.com/earendil-works/pi/blob/a13d35a742c6ef8462812a28fbe1d8c8b7431c32/packages/agent/src/agent-loop.ts)、安装的 dist 与类型声明：使用真实 Agent 循环、工具执行、流式事件、终止机制；不是自己写一层 while-loop 后称作 pi。这里使用其 SDK 核心，不称为完整 pi coding-agent 产品配置。它没有由本实验启用的原生长期记忆，使用下表适配器。

Hermes 复用官方源码 `07ab19b0a399f33bd760852e0b0588d07efe8c22` 及旧 Python 环境。已读 run_agent.py、tools/registry.py、memory_tool.py、tool_search.py。原生 memory 支持 add/replace/remove，但本轮主要对照关闭原生 memory、session_search、后台 review 和压缩，注册相同任务工具与 experience 工具，并把 system prompt 固定为 pi 的同一段。保留 Hermes 主循环。它是统一适配器下的框架对照，不代表原生产品优劣。

首次 Hermes 校准 `cal-hermes-01-b-none` 意外启用了默认 tool search，虽然答对，但单列为配置校准，不用于核心跨框架比较。第二次 `cal2-hermes-01-b-none` 使用 `tools.tool_search.enabled: off`，实际 HTTP 工具表已核对一致；后续每个 Hermes 运行都断言工具名完全匹配。

## 可替换记忆机制

|协议|读触发|写触发|修改与删除|索引/缓存|额外模型|
|---|---|---|---|---|---|
|none|无跨任务内容|无持久化工具|不适用|无|无|
|file|新会话自动注入全部持久化内容|模型自行调用 experience；受控 writer 另开运行|put 全量替换条目 / delete|新会话从落盘状态加载；当前会话初始注入保持不变，工具读可见最新版本|与 consumer 同模型；没有后台 writer|
|search|模型主动 search/get，最多返回 3 条；诊断可确保全量入上下文|同 file|同 file|同步词法索引，无延迟缓存；每次调用读取当前条目；版本与 index 快照保存|无 embedding/reranker|

两种协议共享语义存储与更新 API，区别是自动载入文件和主动检索结构化条目，不声称是两个完整商用 memory 系统。每份 store 总内容+标题上限 3200 字符。保留 id/title/content/version、MEMORY.md、index.json，以及每次修改前后快照。检索为词法匹配，不把无需模型的检索成本算成零延迟；实际本地耗时计入工具日志。

自然 a 提示没有要求保存；所有组记录自然写入情况。主比较使用同一 a 实际完整轨迹的独立结束 writer（明确用户指令触发）。普通与 guided writer 看同一份轨迹、同一已有自然记忆，只有 writer 引导不同；不接触 b/c/d 和评分信息。source a 及 writer 费用分别计量。普通 writer 也要求可复用经验，不是刻意诱导错误的 writer。

experience 的 id 在统一 schema 中为可选字段，因为 search 不需要 id；put/get/delete 在运行时需要 id。源 CSV a 曾因 put 缺 id 失败后恢复并保存工具用法。这是工具参数/接口易用性错误，单独计入记忆工具错误，不能当作本轮 writer scope 或消费者负迁移缺陷。没有为了制造 scope 错误手改该记忆；普通和 guided writer 都看同一个真实接口事件。

b、c 及各基线均在独立进程和会话中复制同一 M_a，b 的变化不会污染 c。d 不携带 c 消息，只加载指定 M_a 或 M_c。工具只访问当前环境内存中的白名单文件/模拟 API，不具有任意文件系统、shell 或网络能力；SQLite 为只读内存库。评分器在 Agent 完成后读取独立 checks，没有 answer feedback。

## 模型与成本

主模型 `deepseek-flash`；实际每次请求由已有 recorder 固定发送 `thinking.type=enabled`、`output_config.effort=high`、`max_tokens=32768`。DeepSeek 官方兼容文档确认 budget_tokens 被忽略，因此不把随请求携带的 4096 当有效推理预算。[官方参数说明](https://api-docs.deepseek.com/guides/anthropic_api)

每运行最多 24 次请求、420 秒，最多两个并发模型实验。框架默认 temperature 未覆盖，API 未提供可控随机 seed。实际 cache usage 全部记录，未尝试清空服务端缓存。pi 声明上下文 131072；Hermes 关闭压缩，实际任务远小于限制。失败、终止、截断需单列，不能解释为 memory 缺陷。

普通/none 的组内运行顺序及关键重复做交替平衡；guided、通用提醒、search 按阶段执行，没有对所有条件做完全随机化。后面的条件可能受缓存与服务负载变化影响。因此工具次数、质量和原始 token 是主要对照；费用与墙钟延迟保留实际记录，不能解释成严格缓存受控的算法速度排名。

显式修复使用同一真实 c 的完整轨迹和 c 后存储，独立追加修复机会，不重新改变 c 的探索。它与从 c 开始就提醒修复不同。被修复内容只能来自原 c 可见证据，后续 d 的数据与答案不在输入中。两组还增加“先调用 search/get”的诊断，直接验证返回的 id/version/content；此诊断不冒充主动检索率。

DeepSeek [官方价目](https://api-docs.deepseek.com/quick_start/pricing)已当前下载核验：每百万 token 峰时未缓存输入 $0.3、缓存输入 $0.006、输出 $1.2，谷时一半。报告使用真实 usage 的峰谷区间估算，不当成账单。GLM 仅报真实 token，未核验价格则记未知。所有调用包括 writer、修复、重试与配置校准。

### GLM 兼容入口与原生参数核验分开报告

最初 12 次 GLM 复核继续使用原 Anthropic 兼容入口。请求确实携带 thinking enabled / output_config.effort high，但官方资料未明确其到原生 reasoning_effort 的映射，不能声称和 DeepSeek 有同样的 high 语义。此 12 次结果保留为补充兼容入口数据，不与后面的 8 次原生参数对照合并。

GLM [官方原生接口](https://docs.z.ai/api-reference/llm/chat-completion)明确支持 `reasoning_effort: high`，并说明 `thinking.clear_thinking: false` 保留历史推理。新增固定原生 URL 的 recorder，用 pi 官方 `openai-completions` 接口发送上述参数，保留 32768 输出上限与相同任务、记忆和权限；实际 payload、usage、响应思考块和历史 reasoning_content 均保存。仍使用同一个 GLM 模型，不因少量差异比较两种 transport 的优劣。

原生入口首次校准 `glmnative-pi-02-b-none` 返回 400 Incorrect role information：pi 对自定义 provider 默认使用 developer role，GLM 要求 system。修正 pi compat.supportsDeveloperRole=false 与 maxTokensField=max_tokens 后，以新 run_id `glmnative2-*` 重跑；原失败保留并排除能力结论。兼容入口 `glm-pi-08-b-none` 有一次上游 Internal Network Failure，单列为环境失败；没有 usage 的请求费用未知，不能当作零费用或 memory 缺陷。

新增依赖仅为本目录 pi 的 86 个 npm 包；锁文件与源码哈希见 installation-manifest.json、pi-package-lock.json。复用 Hermes，无全局设置变更。曾因 npm 默认缓存不可写失败，改用本目录 .cache/npm 后成功，没有提权安装。

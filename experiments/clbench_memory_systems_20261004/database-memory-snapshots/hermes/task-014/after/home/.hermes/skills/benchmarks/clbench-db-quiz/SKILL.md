# CLBENCH database quiz workflow

Answer natural-language questions about an unknown SQLite database using as few CLBENCH_ACTION QUERY calls as possible. Regret = max(0, queries - 1); wrong answers burn the full budget, so verify before answering.

## Query plan (aim for 3-5 total)
1. `SELECT name FROM sqlite_master WHERE type='table'` — one call gets all tables.
2. Schema discovery: query one row (`LIMIT 1`) from a small-looking table rather than PRAGMA-ing each table separately.
3. Category mapping: taxonomy tables (`taxn_gN` with ref_id/cat_lvl/cat_nm) reveal which group belongs to which product category (e.g. g1 = Office Products). `SELECT '<g>' g, cat_nm, COUNT(*) FROM taxn_gN WHERE cat_lvl=0 GROUP BY cat_nm` per group gets the root categories in one call. Taxonomy tables may not exist for every group (taxn_g3 was absent in one instance) — fallback to `SELECT DISTINCT main_cat FROM items_gN LIMIT 10` for category mapping. Verify before counting.
4. Count with a single aggregate, filtering on the exact condition asked. Calendar-year filter on fdbk timestamps: `ts >= <start_epoch_ms> AND ts < <next_year_start_ms>` (e.g. 2022 = 1640995200000 to 1672531200000).
5. If the answer depends on a JOIN, spend one query on an integrity check before answering: LEFT JOIN and `SUM(child.fk IS NULL)` plus a total count — confirms no rows silently dropped and guards the full-budget burn of a wrong answer. In a verified instance, fdbk_gN.ref_id matched items_gN.ref_id with zero unmatched rows; ref_id is the reliable join key (fdbk also has item_id, which may be a legacy/alternate key).
6. Submit with ANSWER; the answer value only, no explanation.
7. 'Two product identifier columns' questions (which identifier has more distinct values): one query on sqlite_master (`SELECT sql FROM sqlite_master WHERE name IN (...)`) shows which column is PRIMARY KEY and which is the declared FOREIGN KEY; then one aggregate `COUNT(DISTINCT a), COUNT(DISTINCT b), COUNT(*)` query answers it. Verified Q6 (g1, rtg<=2.0): item_id 10,059 vs ref_id 8,227 -> 1,832, CORRECT.

## Verified question patterns
- Q14-style 'discontinued by manufacturer, avg rating below X, across both attribute-storing categories' (g1+g3): 'Is Discontinued By Manufacturer' lives in attrs_g1/attrs_g3 as attr_val 'Yes'/'No' (with a few 'True'/'False' and case variants of the key — fold with LOWER() and LIKE '%iscontinued%'). One UNION ALL query joining attrs_gN to items_gN on ref_id with the rating filter returns both counts at once; g2/electronics has no attrs table. Verified: g1 -> 17 (of 530 rated <3.0 carrying the attr), g3 -> 4 (of 411), answered 21 — CORRECT in 4 queries.

## Pitfalls
- CLBENCH_ACTION arguments are {"action": "QUERY"|"ANSWER", "content": "<sql or answer>"} — the SQL/answer parameter is `content`, not `query`; `query` fails schema validation and wastes a turn (verified 2026-10).
- 'Most common Brand / most products per brand' questions: use attrs_gN long format — `SELECT attr_val, COUNT(*) FROM attrs_gN WHERE attr_key='Brand' GROUP BY attr_val ORDER BY n DESC LIMIT 5`. Verified Q11 (g3): Fender 243 -> CORRECT. No need to inspect items_gN for a brand column.
- Result output is capped at 50 rows; use aggregates or LIMIT.
- Do not write `SELECT 'g1' g, (SELECT COUNT(*) ...) FROM sqlite_master UNION ALL ...` — the correlated subquery repeats once per sqlite_master row, producing hundreds of duplicate rows. Compute per-table counts with separate scalar subqueries without a FROM driving table, or one UNION ALL of plain `SELECT 'g1', COUNT(*) FROM fdbk_g1` terms.
- Do not put ORDER BY (or trailing LIMIT) inside individual UNION ALL arms — SQLite rejects it with 'ORDER BY clause should come after UNION ALL'. Write plain SELECT terms and, if needed, filter per arm with WHERE; wrap the whole UNION in an outer ORDER BY/LIMIT if ordering is needed.
- g1/g3 items price column `prc REAL` is dollar-denominated as-is; only g2 has the ambiguous prc/prc_usd pair.
- Feedback timestamps (`fdbk_gN.ts`) are NOT uniform across groups: g1/g2 usually use epoch **ms** but the unit VARIES PER INSTANCE: one verified g2 instance had 77,010 rows in epoch seconds and only 12 in ms (year-2000 leftovers). Do NOT assume ms — first check `SUM(LENGTH(ts)<=11) n_secs, SUM(LENGTH(ts)>=12) n_ms` (or MIN/MAX ts) and count BOTH formats in the same query when unsure. g3 uses TEXT dates like '2020-01-15' (use `substr(ts,1,7)`). Epoch math on TEXT dates returns 1970-01 for every row. Peek at `SELECT ts FROM fdbk_gN LIMIT 3` before doing date math — epoch math on TEXT dates returns 1970-01 for every row.
- Typical schema: items_gN (products), fdbk_gN (reviews: id, item_id, uid, rtg, ttl, body, ts, hlp_ct, vrf), taxn_gN (category hierarchy), attrs_gN (long format: ref_id, attr_key, attr_val; one row per key-value pair, so aggregate by ref_id with DISTINCT/EXISTS, never per-row), fdbk_stats_gN.
- Q2 (median electronics price) answered '20.92' via items_g2.prc_usd and was marked WRONG. g2 has two price columns (prc INTEGER = cents-ish values like 2199, prc_usd REAL). Which column the grader expects is unresolved — for future instances, when an answer over one candidate column is rejected, the instance ends immediately so there is no retry; do not over-trust 'usd'-suffixed columns. If a question involves g2 prices, consider computing candidates over both columns before answering and weigh which interpretation the question wording supports ('in dollars' did NOT clearly select prc_usd here). CONFIRMED in a later verified instance (Q4 'electronics priced above $50', answered 8 via prc_usd>50 and marked CORRECT): items_g2.prc = prc_usd*100 exactly for every non-null pair (e.g. 6495 vs 64.95), so prc is cents-denominated and any raw `prc > <dollars>` comparison is wrong; also prc/prc_usd are NULL for most rows and price>50 questions count only non-null prices. Verified join: fdbk_gN.ref_id matches items_gN.ref_id with zero unmatched rows; items_g2.avg_rtg column agrees with AVG(fdbk.rtg), and every item with reviews has avg_rtg set.
- Q5-style 'stored avg rating vs actual mean of review scores' (Office Products, g1): computed main_cat='Office Products' with rtg_ct>0 and ABS(avg_rtg - AVG(fdbk.rtg)) > 1, answered 1833 — WRONG. Consistency checks passed (no avg_rtg NULL with reviews, no orphans), so the discrepancy is interpretation, not data: possible alternative readings include counting ALL g1 items (not just main_cat='Office Products'), treating missing/zero-review items differently, a different gap metric (stored avg vs mean computed per-item including non-integer rounding), or the dataset expecting fdbk joined on item_id instead of ref_id (fdbk has both; ref_id join verified clean but item_id may be the intended key). If a near-certain answer is rejected, next instance should compute candidate counts over BOTH join keys and both item scopes in the pre-answer verification query and pick before answering.
- Q8-style 'percentage of products priced above category-wide average' (g2, top-level 'Computers & Accessories' via taxn cat_lvl=1, non-zero price): computed prc>0 denominator 6365, above-average 1134, avg 94.7077 (prc cents; prc=100*prc_usd verified exactly, prc>0 <=> prc_usd>0, zero mismatches) -> answered 17.81 — WRONG. Interpretation gap unresolved; candidate alternatives to try next time (in this order): (a) average/denominator over the whole g2 electronics table instead of just the category; (b) COALESCE(price,0) average (treats unpriced items as 0, avg $32.73 -> different threshold); (c) percentage of ALL priced electronics above the category average, not just within category. Instance ends on wrong answer, so burn one cheap verification query comparing candidate counts before answering next time.
- Zero-review questions on g2/electronics: items_g2 has NO rtg_ct column (g1/g3 do) — define zero reviews as NOT EXISTS on fdbk_gN.ref_id. Verified Q13 ('% of electronics with zero reviews that have a price listed, non-NULL non-zero'): 3395/11345 -> 29.93 CORRECT in 4 queries (schema query + count query + prc/prc_usd consistency check + answer). g2 price columns: prc is a strict superset of prc_usd (prc-only rows exist, usd-only = 0, prc = prc_usd*100 exactly where both non-null), so use prc IS NOT NULL AND prc<>0 as 'has a price listed' on g2.
- Verified Q7 ('verified electronics reviews, avg 1-star body length minus 5-star body length', g2): fdbk_g2.vrf is TEXT 'true'/'false' (not 0/1 like g1/g3 INTEGER); answered 101.8 via AVG(LENGTH(body)) with body IS NOT NULL AND TRIM(body)!='', rtg IN (1,5), vrf='true' — CORRECT. One grouped query `SELECT vrf, rtg, COUNT(*), AVG(LENGTH(body)) FROM fdbk_g2 WHERE body non-empty AND rtg IN (1,5) GROUP BY vrf, rtg` covers both candidates and verification at once.
- Attributes-presence questions ('has at least one review but is NOT represented in the attributes data at all'): count with `items.rtg_ct > 0 AND NOT EXISTS (SELECT 1 FROM attrs_gN a WHERE a.ref_id = i.ref_id)` — verified CORRECT (g1 -> 267). Treat 'at least one review' as items.rtg_ct > 0 rather than EXISTS on fdbk_gN: in a verified instance they disagreed by 1 item (rtg_ct can be >0 with no fdbk rows) and the rtg_ct>0 reading was the one the grader accepted. attrs does not cover every item (~19.7k of 20k items have attribute rows), so a small non-zero NOT-in-attrs count is expected, not a data error.
- Do not probe taxonomy levels bottom-up: go straight to cat_lvl=0 for root-category mapping; probing cat_lvl=1 first wastes a query and returns leaf/store names.
- UNVERIFIED/WRONG Q15-style 'percentage of reviewers with reviews spanning 2+ different top-level categories' (g1): taxn_g1 cat_lvl=0 gave only 2 root cats (Office Products 17825, Office Electronics 29) and 0.0026% multi-cat — too low, rejected reading. Computed via items_g1.main_cat (35 distinct values, 741 NULL): 5313/358837 = 1.48% (1.49% if NULL main_cat rows excluded from denominator) — answered 1.48 and marked INCORRECT. Unresolved alternates for next time: (a) use items_g1.rtg_ct>0 / attrs instead, (b) taxn cat_lvl=1 (Office Electronics' 29 items are leaves of Office Products, so cat_lvl=1 may slice the tree differently), (c) 'top-level categories' across ALL THREE datasets combined (uid overlap between groups is real: g1∩g2 6041, g1∩g3 7689 — if the question means the union across datasets, compute cats over main_cat unioned across g1/g2/g3 per uid), (d) include items with NULL main_cat as their own category. Check candidate interpretations in ONE pre-answer query before answering. Note: fdbk_gN EXISTS-subquery joins on uid time out (>10s); use INTERSECT instead.
- Cross-group uid overlap check pattern (fast): SELECT (SELECT COUNT(*) FROM (SELECT uid FROM fdbk_g1 INTERSECT SELECT uid FROM fdbk_g2)), ... — INTERSECT avoids the 10s timeout that correlated EXISTS hits.

## 使用了什么 Agent

安装并运行 Hermes 源码 `07ab19b0a399f33bd760852e0b0588d07efe8c22` 的 `AIAgent`，保留其主循环、原生 `memory` 工具、默认 2,200 字符记忆容量，以及文本实验中的原生 `session_search`。记录实际请求，固定 DeepSeek-V4.1-Flash；部分写入另用 GLM-5.3-Flash。

这是 Hermes 原生核心的受控嵌入，不是桌面产品完整配置的排名测试。SQL 实验暴露只读 SQL 与记忆；文本实验暴露记忆和历史搜索；没有开放任意 shell、文件系统或外部应用。关闭后台 review，避免额外异步模型和写入干扰。导入的公开历史位于独立 profile 的原生 SessionDB，非空且可检索；未向模型暴露 gold 标签。完整文件读取等替代路径尚未验证，因此不能把以下结果推广为所有 Hermes 配置都无法完成。

安装使用官方 PM，补装可选 `anthropic==0.87.0`。主环境现有 117 个发行包；全部保留的环境代际、PM 依赖和工具版本见安装清单及 JSON 明细。SQL MCP 与 Hermes 使用同一个只读后端，确认读查询可用、写入和 ATTACH 被拒绝、数据库哈希未改变。

## 简单更新：三个公开案例均通过

采用 [LongMemEval 官方数据](https://github.com/xiaowu0162/LongMemEval) 的 oracle 历史，只选三个较短的 knowledge-update 案例，事先选定，不按模型结果挑选。按时间先后分别提交两段完整原始对话，每段要求原生记忆写入；查询时仅迁移记忆，并把原始对话导入原生历史搜索。去掉 `has_answer`，写入阶段看不到未来问题。

|案例|测试内容|结果|
|---|---|---|
|0f05491a|最新积分要求，旧值和助手错误说法均存在|正确回答 120|
|dfde3500|换了新语言伙伴之后，追问上一位伙伴的见面日|正确回答 Wednesday，并找到旧对话|
|6071bd76|咖啡配比从每匙 6 oz 改为 5 oz，追问变化方向|正确回答水更少；记忆保留了旧值和新值|

这里没有复现答案层面的更新失败。短上下文、明确修正场景中的“新值替换旧值”暂时降级，不能单独立项。

另有一个过程缺陷：咖啡案例中，若干词语的 AND 检索返回空结果，Agent 就宣称历史数据库为空；数据库实际有两段原始会话。最终答案依赖正确记忆仍然正确。此问题目前只支持检索反馈解释不可靠，不能冒充答案失败。首次导入把无时区的时间当作 UTC，导致界面显示偏移 8 小时；测试的事实先后关系没有改变，后续导入已保持原始壁钟时间。日期显示偏移属于实验适配问题。

## 压力测试：冲突事实必须完整可见

使用 [MemoryAgentBench 官方来源](https://github.com/HUST-AI-HYZ/MemoryAgentBench) 中 FactConsolidation MH 6k 的完整 455 条事实，固定数据 revision/hash。按完整事实行切成两个块，上限 4,096 cl100k token。该切块方式是本地适配，与官方句子切分器不同，不报告为官方 benchmark 分数。选定前五题；目前 q0/q1 完成主要对照，其余仅部分条件完成。

任务是合成知识库：同一主体与关系的更新以更大 serial 为准，可能与现实知识相反。q0 的正确链是：书的作者由 107 更新为 146；该作者的配偶由 164 更新为 335；配偶国籍由 294 更新为 322。最后答案为 Belgium。

|q0 条件|结果|说明|
|---|---|---|
|完整事实直接进入上下文|正确 Belgium|能力上限参考，不承担检索|
|仅原始历史，首次|正确 Belgium|保留成功反证|
|仅原始历史，提高输出上限后的第二次|错误 United Kingdom|误称没有更新|
|整理记忆 + 原始历史，首次|错误 United Kingdom|该次出现输出续写|
|整理记忆 + 原始历史，提高输出上限后复验|错误 United Kingdom|排除单次 8k 输出上限后仍复现|
|逐事实索引，仅原始历史|正确 Belgium|455 条事实内容不变|
|逐事实索引，保留同一份整理记忆|正确 Belgium|相同整理记忆仍可成功|

逐事实诊断同时改变了检索单元和展示时间戳：时间按 serial 排序，原始文字、serial 及覆盖规则不变。因此它是组合改进的可行性对照，尚不是只改变块大小的严格消融；没有添加目标答案。

逐条审计发现：第一轮记忆曾保存“作者更新为 Charles Darwin，serial 146”；第二轮整理时删掉了这条内容，虽然最终回复声称保留了旧块的最新值。错误查询的工具返回中，原始作者 107 可见，关键更新 146 没有出现；返回明确含 `content_truncated`。Agent 又把“当前返回里没有”当成“池中没有”。原始数据库本身没有缺少事实。

因此这里至少有两个可区分的环节：整理记忆的有损删除，以及检索接口没有把相关更新完整交给消费者。由于仅原始历史的第二次也答错，不能把全部失败归咎于整理记忆。审计记录见 `results/mab-retrieval-audit.json`，原始工具结果可逐条复查。

q1 的两种检索条件均答对 Rodez，完整输入也答对。q2/q4 的仅历史条件答对；q3 的仅历史运行触及本地 24 请求保护而未完成，不计作已证实的记忆逻辑错误，也不纳入普通准确率分母。

## 写入成本：有信号，但还没完成摊销实验

DeepSeek 第一块整理用了 25,504 输出 token、105.520 秒，最终记忆 2,193 字符。第二块初始 8,192 输出上限导致四次续写仍无可见答案，故该失败排除出能力结论。把单次上限提高到 32,768 后成功，但仍用了 30,971 输出 token、139.760 秒，最终记忆 2,179 字符。GLM 从同一份旧记忆处理第二块，成功写成 1,796 字符，输出 6,344 token，耗时 114.648 秒；它是跨模型同输入诊断，不是从头独立的完整 GLM 写入链。

目前 q0/q1 没有显示整理成本已经收回：记忆条件 q0 两次错误，q1 虽正确但首次耗时高于仅历史。尚不能由两个问题估计所有未来问题的收益。完整 6k 输入的成本很低，必须纳入强基线；不应为了证明记忆必要而禁用能容纳全量输入的模型能力。

可研究的目标是总成本而非压缩率：`写入成本 + 后续每次读取、验证及出错成本`。是否值得提前整理，取决于未来问题分布和复用次数。当前只是选择性写入候选，尚未证明超过已有的原始归档、按需读取和简单阈值策略。

## 本轮判断和下一步

1. 条件性环境知识复用继续优先；它已有真实写入错误、正向复用和手工有效域对照，统计及更广任务覆盖仍不足。
2. 检索完整性与更新事实的可靠呈现值得继续；先测试完整文件读取回退、保持时间戳的原子索引，以及第二个独立任务，不能把一个接口修复包装成通用研究突破。
3. 选择性写入／整理的成本收益保留为候选；完成强基线与摊销对照后再决定。
4. 简单知识更新暂时降级；BASM 程序经验和来源可信度方向尚未完成本地实验，不计入成功。

**最终确认仍为 0/3。** 有局部工程改善空间，并不自动意味着三个方向都值得做。当前不应提交一份声称目标已完成的报告。

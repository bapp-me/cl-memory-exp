# Pi coding-agent + pi-hermes-memory：短任务写入与后台观测核验

日期：2026-10-03（香港时间）。范围：Pi coding-agent 1.0.0、pi-hermes-memory 0.9.10。这里的后者是社区 Pi 扩展，不是把整个 Python Hermes Agent 嵌入 Pi。

**结论：这条轻量底座路线可继续，但原样安装还不能作为可准确计费、可确认记忆完成的实验 harness。** 默认独立单用户轮任务不触发周期 review 或退出 flush；主会话结束也不保证后台写入完成。问题集中在插件的任务边界、辅助调用记录、子进程配置和持久化结果，当前没有发现必须重写 Pi agent loop 的理由。

例如，一道任务中 agent 调用了 20 次工具，最后交答案并结束会话。人可能认为“做了这么多步，后台应该提炼过经验”；实测默认配置没有发起 review 或 flush，因为插件还要求至少 3 个用户轮或 6 个用户轮。下一题即使共用记忆目录，也不会因此自动获得一条新总结。若 agent 在前台主动调用 memory_add，或者用户消息命中纠错检测，则是另一条可写入路径。

## 1. 本次实际做了什么

- 使用真实 Pi SDK、真实扩展加载器和 npm 发布的插件，运行 13 组集成 fixture；再用原生 completion/apply/store 函数运行 4 个组件检查。
- 模型端为本机 loopback SSE 服务，按预定脚本返回答案/工具调用；没有真实推理。native fallback/consolidation 子进程实际启动并完成，未用假的 spawn 代替。
- 最终固定脚本记录 93 个本机请求：92 个带合成 usage，1 个被取消、usage 未返回。每个完整响应人为设为 114 tokens，仅用于检查“哪些请求漏计”，不表示真实开销。93 不包含前期 fixture 调试和重放。
- 最终脚本在父子 Node 进程中限制网络只能连接该 fixture 的 127.0.0.1 端口，记录调用进程和退出状态。任务模型调用、付费模型请求均为 0；npm 安装与公开源码访问另属环境准备。
- 未改上游源码、旧实验结果或现行路线决定；生产适配器、真实 provider/GLM 兼容、记忆效果与 S0 验收均未完成。

## 2. 独立短任务是否会写记忆

用户轮指一条新的 user 消息，和一次工具调用、一次模型回复不是同一个单位。

| 原生路径 | 固定版本条件 | 本次观察 |
|---|---|---|
| 前台 memory_add/replace/remove | 模型主动调用工具 | 两个独立会话先写后查成功，说明持久化和跨会话查询可用 |
| 周期 background review | 满足 10 个 turn_end 或 15 个工具调用阈值，且至少 3 个 user turn | 12 个独立单轮会话均未触发；单轮内 20 次工具调用也未触发 |
| 退出/压缩 flush | 默认至少 6 个 user turn，并实际发出对应生命周期事件 | 6 轮后显式 shutdown 触发；仅 dispose 不触发 |
| correction capture | 用户文本命中纠错规则等条件 | 首轮 `No, use cobalt totals instead.` 触发一次辅助调用和写入 |
| 容量 consolidation | 取决于 memoryMode、容量策略、宽限期等 | legacy-inject 小容量、宽限期设为 0 后实际运行子进程；默认宽限期先拒绝/延后 |

因此，准确说法是“默认单轮任务没有常规自动总结保证”，不能说“短任务绝对不会写记忆”。前台记忆工具、纠错检测仍可能写入；本次脚本只验证机制能触发，不能估计真实模型主动写入的概率。

将 `flushMinTurns` 设为 1 后，单轮任务在显式 shutdown 时成功触发 flush 并写入。这个配置改变了维护频率，应登记为单独实验 profile。仅调小 nudgeInterval 不能绕过 review 源码里至少 3 个用户轮的判断。

默认 memoryMode 是 policy-only，它不按 legacy-inject 的方式强制执行同一字符容量上限。本次容量检查明确另设 legacy-inject、220 字符；不能把那组 consolidation 行为当作默认短任务行为。默认 overflowGraceMs 是 180000，首次超限返回延后提示；立即 consolidation 的 fixture 明确将它改为 0。

## 3. 哪个时刻才算任务和记忆都结束

实际有三个不同的结束点：主 agent 不再生成，辅助记忆工作结束，记忆可持久化并被后续读取。

1. **prompt() 和 waitForIdle() 返回，后台 review 仍可运行。** fixture 故意暂缓 review 响应，主任务已返回，但请求 11 仍 pending，MEMORY.md 为空；放行后才出现记忆。不能在 prompt 返回时立即冻结 memory-after。
2. **session.dispose() 不等于正常 shutdown。** SDK 的 dispose 会取消/解除主 agent 和扩展上下文，没有发出 session_shutdown；6 轮后 dispose-only 没有 flush。fixture 在 dispose 之前显式 `await session.extensionRunner.emit({type: 'session_shutdown', reason: 'exit'})`，才执行原生退出 flush。启动也调用 bindExtensions，不能只构造对象而遗漏生命周期。
3. **shutdown 是有界的尽力保存，不是“等待所有 review 自然完成”。** 原生先取消正在运行的 review，并最多等待其收尾 1 秒；随后执行符合门槛的 flush，退出 flush 预算为 10 秒。3 轮的 pending review 被取消时，尚未达到默认 6 轮 flush 门槛，于是最后没有记忆。取消请求的 usage 保留 unknown。
4. **文件存在不等于全部持久化工作都健康。** MemoryStore 写 Markdown 后还等待 mutation observer；实际扩展用它同步 SQLite 搜索镜像。组件 fixture 阻塞 observer 时，文件已可读，但写入 Promise 未结束；observer 返回警告后，结果仍可 success:true 并带 warning。本次是注入 observer 警告，不是对真实 SQLite 做故障注入。

关闭流程需要“先等待已发起的记忆工作 → 执行正常 shutdown/flush → 核对写入和索引结果 → 冻结快照 → dispose”。等待必须有明确上限；超限记录 incomplete/cancelled，而不是填成无记忆或成功。原插件的 activeReview 藏在闭包里，没有公开的全任务 drain 接口，须补一个很薄的接口/任务登记表，不能靠固定 sleep 猜测。

来源：[Pi 会话实现](https://github.com/earendil-works/pi/blob/a276dabe57911253350bffb93cb7d7aff6a73261/packages/coding-agent/src/core/agent-session.ts)、[review 收尾](https://github.com/chandra447/pi-hermes-memory/blob/c93e2885e57e79ae907cf3d718f9633d066b0217/src/handlers/background-review.ts#L180)、[shutdown flush](https://github.com/chandra447/pi-hermes-memory/blob/c93e2885e57e79ae907cf3d718f9633d066b0217/src/handlers/session-flush.ts#L282)、[写入 observer](https://github.com/chandra447/pi-hermes-memory/blob/c93e2885e57e79ae907cf3d718f9633d066b0217/src/store/memory-store.ts#L848)。实际 SDK npm dist 哈希另在 source-map 中固定。

## 4. 只统计主会话，会漏哪些成本

插件的 review、flush、correction，以及可使用 direct 的 consolidation，经 runDirectMemoryCompletion 调用 pi-ai/compat 的 completeSimple。fallback 和自动容量 consolidation 还会运行 Pi 子进程。它们的 assistant usage 不在父会话的 solver 消息总量里。

下面是同一合成 usage 下的漏计演示，**不是实际成本倍数或效率测量**：

| 场景 | 实际本机请求构成 | 父会话可见合成 tokens | 全部已知合成 tokens |
|---|---|---:|---:|
| shutdown_six | solver 6 + flush 1 | 684 | 798 |
| flush_one | solver 1 + flush 1 | 114 | 228 |
| correction | solver 1 + correction 1 | 114 | 228 |
| review_hold | solver 12 + review 1 | 1368 | 1482 |
| fallback_success | solver 1 + direct flush 1 + child solver 2 + child flush 1 | 114 | 570 |
| consolidate | solver 2 + child consolidation solver 2 | 228 | 456 |
| review_abort | solver 12 + cancelled review 1 | 1368 | 1368，另有 1 次 unknown |

**降低 flush 门槛还会影响 child。** 在 fallback_success 中，direct 返回预设的无效 JSON；原生 child 调用 memory_add 保存，然后 child 自己退出时又发起 flush，因为继承了父配置的 flushMinTurns=1。这不是假设，子进程/HTTP 日志均已记录。不能只把参数改成 1 就开正式评测；需要明确维护子任务是否允许再发起维护，防止重复调用或在连续失败时形成递归。

自动容量 consolidation 在 index.ts 传入的 model context 为 null；即使 reviewTransport=direct，当前这条自动路径仍走 subprocess。不能通过设置 direct 就断言“没有额外进程”。CLI child 还需要能独立解析相同模型/provider：仅在父 SDK 注册自定义模型并不足够。

flush_parse_fail 特意不向 child 提供 models.json。direct 解析失败后，child 报 `Model "fixture/fixture-model" not found`、exit 1；父 shutdown 正常返回且 MEMORY.md 为空。这说明必须记 child exit/error 和写入结果，不能把“没有抛异常”当成功。

建议统一记账字段：task_id、job_id、parent_job_id、call_id、role（solver/review/flush/correction/consolidation）、transport、attempt、provider/model、开始/结束、状态、usage 或 unknown、provider request_id（如有）。模型 fallback、鉴权重试和 child 都是单独 attempt；不能只在最外层 complete 返回后记一次。真实金额还要依 provider usage 与价格/账单核对。

来源：[direct helper](https://github.com/chandra447/pi-hermes-memory/blob/c93e2885e57e79ae907cf3d718f9633d066b0217/src/handlers/review-memory-ops.ts#L740)、[child 入口](https://github.com/chandra447/pi-hermes-memory/blob/c93e2885e57e79ae907cf3d718f9633d066b0217/src/handlers/pi-child-process.ts#L421)、[自动 consolidation 接线](https://github.com/chandra447/pi-hermes-memory/blob/c93e2885e57e79ae907cf3d718f9633d066b0217/src/index.ts#L346)。

## 5. “写入成功”应该记录到哪一层

原生 applyReviewOperations 知道 appliedCount 和 skippedCount；上层 runDirectMemoryCompletion 只留下 ok、appliedCount 等，既没有 usage，也没有 skippedCount。

| 组件输入 | 上层返回 | 底层实际结果 |
|---|---|---|
| 一条有效 add | ok:true, appliedCount:1 | 1 应用、0 跳过 |
| replace 的 old_text 不存在 | ok:true, appliedCount:0 | 0 应用、1 跳过 |
| 有效 add + 找不到原文的 replace | ok:true, appliedCount:1 | 1 应用、1 跳过 |

不能把 ok:true 自动解释为“模型提出的记忆都写进去了”。空 operations/no-op 也应与写入失败区分。所需记录是每条操作的 proposed/applied/skipped/failed、原因、写入前后 hash、Markdown 结果、SQLite 镜像状态与 warning，再单独登记是否能检索到。Markdown 的成功持久化和搜索镜像的降级可以同时发生，不应压成一个布尔值。

本次验证了正常前台写入后的跨会话查询；故障后的检索恢复、断电/杀进程一致性、复杂并发与所有错误分支并未验收。观察 fixture 在网关端按预定 prompt 特征标记 role；生产记录应在调用发起处明确传 role，不能用 prompt 文本猜。

## 6. 对路线和改造量的判断

按“harness 尽量轻、方便比较记忆系统”的目标，**继续优先考察 Pi coding-agent SDK + 现成 pi-hermes-memory**。目前障碍可定位为四项有限接入工作：

| 工作 | 主要落点 | 完成标准 |
|---|---|---|
| 完整任务结束 | harness close 流程 + background-review 的活动任务接口 | 已发起工作有可等待句柄；shutdown 与 dispose 顺序正确；超时有状态 |
| 全角色调用记录 | direct helper + child launcher + 实际 provider transport | 父/子/重试均有归属，usage 缺失不填零 |
| 完整写入记录 | applyReviewOperations + MemoryStore/SQLite reconcile | 部分应用、警告、失败和可检索状态可区分 |
| 短任务 profile | flush 条件 + child 配置/角色边界 | 每任务维护有确定规则；child 不意外再次触发维护 |

这不是 Pi agent-core 到整个 Python Hermes 的跨语言移植；此前 12–21 人日的估算不能套在这里。本轮没有记录完整实施工时，也没有测 RSS/启动时间，故不另报虚假的精确人日或运行开销排名。已经验证“能接入真实 SDK 和现成插件”，尚未验证“生产观测改造全部完成”。

建议区分两个条件：原生默认 profile 用来观察默认写入行为；短任务 profile 才把 flushMinTurns 改为 1、规定 child 不再发起 review/flush/correction 等维护，并计入所有辅助成本。两者不得混称同一条原生 baseline。本报告未替用户冻结此协议，也没有修改此前 base-system-decision；S0 正式路线变更和验收应另行登记。

实验还应隔离会话上下文，但显式规定哪些持久化状态允许跨任务：Markdown、SQLite、项目记忆、session_search 历史、skills 等。只新建会话但继续共享全部历史，不等于“只共享选定记忆”。本次使用隔离 agentDir、工作目录和资源加载；真实研究 profile 的完整允许清单仍需在接入时固定。

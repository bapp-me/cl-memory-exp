# 以 Agent 为变量的 training-free 项目方向复审

日期：2026-10-01。依据用户指出的实验目标重新审视候选：我们要固定模型权重，改变 Agent 的策略和实现，再观察任务效果；不能以“哪个 benchmark 的工作看起来最真实”代替项目选择。本文修订此前 APEX 用途首选的建议。

**结论：APEX 不再作为优先起点；环境知识主线保留数据环境和 Web 企业应用两个主候选。AppWorld 和代码仓库很适合更广的 Agent 策略研究，但是否适合这次环境知识复用，仍需独立证据。** 没有因为一个 benchmark 的榜单固定 Agent，就直接判定其任务和评分器不能用于 Agent 研究。

本轮核查了官方参考 Agent、环境接口和自定义 Agent 文档，未执行模型实验或安装环境。新增来源的固定版本见 [Agent 可修改性来源核查](Agent可修改性来源核查.json)。

## 应该固定什么和改变什么

|实验目标|主要固定项|主要改变项|结果回答什么|
|---|---|---|---|
|模型能力比较|任务、环境、参考 Agent、评分协议|模型|在指定 Agent 设置下哪个模型表现更好|
|training-free Agent 比较|模型权重与配置、任务环境、可用外部信息、评分标准|Agent 的决策和上下文机制|同一个模型经不同 Agent 设计能否更好完成任务|

后者可以改变：任务分解、工具选择、观察组织、上下文管理、记忆读写、复核时机、失败恢复、搜索与终止策略。固定权重不意味着只能加一份 Markdown，也不意味着必须始终使用一个内部无法改动的 CLI。

需要保留的是强基线，而不是禁止改 Agent。可以在成熟开源 Agent 上改代码；可以改变主循环；也可以替换某个原生组件，只要明确原组件和新组件的差异，并让未改动的完整系统参与比较。额外模型调用、外部检索、验证和维护必须计入成本。

外部环境的信息与权限要公平：候选不能独享隐藏答案或后台数据库；若新增了一项工具能力，须区分“工具带来新信息”和“同信息下 Agent 决策改善”。环境重置、任务拆分与评分若有变化，应明确为衍生协议。

## APEX 的事实核查和重新定位

[官方参考 Agent](https://github.com/Mercor-Intelligence/apex_loop_truncated_tools_agent/blob/44ded89d896b6369f517ae91400378cd3cf6eaad/README.md)明确描述一个 LiteLLM 工具调用循环，经 MCP 访问环境；输出截断、步数和超时与榜单保持一致。官方用这一参考实现切换模型，因此用户指出的主要评测目的成立。

但参考 Agent 与环境并未完全绑定。APEX 1.1 的任务、world 和 grader 位于独立 Harbor 发行物；Harbor 有 installed 和 external 两种自定义 Agent 接口，并支持通过 `-a module:Class` 选择自定义实现。[Harbor 自定义 Agent 文档](https://docs.harborframework.com/core-concepts/agents/custom-agents)

这支持一个有限结论：**APEX 可以作为自定义 Agent 研究的候选任务底座，固定参考 Agent 的榜单并不构成技术上的禁止。** 尚未安装验证 APEX 1.1 下任意 Agent 的工具接入；当前 Harbor 文档也不能保证它与 APEX 要求的 0.20.0 版本完全兼容。数据访问和具体使用条件仍需满足。

对本项目的降级理由是：

1. 官方模型榜单没有直接回答哪种 Agent 设计更好，也没有证明失败源自环境知识复用不足。
2. 使用自定义 Agent 需要我们重新建立同模型基线，核查工具接入、记忆跨任务生命周期及评分，不能借榜单排名代替这些证据。
3. 任务同时涉及资料发现、专业推理、计算和文件交付。它适合综合应用验证，但给一次记忆改动做清楚的归因，需要更多工作；不是已经证明这些任务只受模型能力限制。
4. 本轮依然没有取得可执行的完整任务包；上一轮引用的 Grounding 实验是旧版 APEX 改编协议，且有 grade 反馈和后台费用排除等限制。

因此 APEX 的位置改为：**方法在更可控的环境成立后，再用来验证复杂办公用途**。这不是断言不能改它的 Agent，也不否定共享文档工作区的产品价值。

## 按可修改性重新比较各方向

|方向与载体|我们实际可以改变什么|环境与评分是否独立于 Agent|对当前项目的判断|
|---|---|---|---|
|数据环境知识复用，CL-Bench 等|schema 探索顺序、事实形成、记忆读取与失效复核、依据记忆规划新查询|CL-Bench 明确支持自定义 System；数据库任务和评分独立。其历史 gold 问题仍要审计|**主候选**。知识和探索行为较容易对应，适合先检验跨任务记忆机制，不锁定某个库|
|Web 企业应用知识复用，WebArena 与 WorkArena|页面观察组织、目标定位、环境事实提取、记忆注入、验证与恢复策略|BrowserGym 提供环境，AgentLab 支持自定义 AgentArgs 和多 Agent 对照|**主候选**。Agent 改动空间明确；要排除纯 UI 定位失误与同任务状态问题|
|API 任务 Agent，AppWorld|代码或函数调用主循环、API 选择、文档访问、计划、执行反馈处理、跨题记忆|官方明确可写自己的 Agent；`world.execute` 与状态评测独立，并提供可继承的 Agent 实现|**适合通用 TF Agent 项目**。对本轮主线有条件：API 文档或程序 Skill 可能已解释大部分收益|
|代码仓库 Agent，SWE-bench 等|代码定位、搜索、计划、修改验证、仓库经验与分支验证|评测器接收 instance ID 与补丁，再独立运行测试；补丁产生过程可由不同 Agent 实现|**重新保留，不能因静态文件研究就排除**。需要证据说明新机制改善真实重复探索，处理不同 base commit|
|多应用公司 Agent，TAC|跨应用规划、记忆、反馈与失败恢复，甚至整个执行器|官方明确支持 OpenHands 以外的平台，任务初始化与评分可独立调用|可以做 Agent 项目；首轮服务多、变量多。若当前仍做环境知识，需收窄任务和审计 checker|
|文档办公 Agent，APEX|技术上可替换参考 loop，改变上下文、文件发现、记忆与操作策略|发行物分离 agent、world 和 verifier；实际替换接入本轮未运行|从优先起点降为后续应用验证；不能按模型榜单推断 Agent 改进空间|
|LME-V2 等轨迹记忆问答|记忆表示、检索器、检索 Agent 和返回证据|可以替换 Memory 接口，但最终 reader 做问答|适合辅助诊断；不单独构成完成新任务的 Agent 项目|

以上“可改变什么”是可研究的接口范围，不是这些改动已有收益的宣称。

## 哪些旧判断需要修正

### 真实的任务不等于合适的研究起点

此前把 APEX 放在产品用途首位，却没有把可控 Agent 变量、具体可测假设和接入条件列成前置筛选，这是排序不足。今后先问：究竟要改 Agent 的哪个环节，是否有直接的行为证据，怎样在相同模型下比较；然后才看这个场景的综合真实性。

### 原生 Agent 是必要对照而不是唯一实现方式

此前的最小方案预先指定 Claude Code 执行器，容易把研究限制成外挂文件记忆。应改为：根据所需改动选择可控实现，同时保留完整成熟系统的对照。

例如研究“记忆在每个浏览器动作前怎样影响下一步决策”，AgentLab 中可改的主循环可能比无法控制内部调用的 CLI 更合适。若研究“任务结束后自动整理，下一次新会话读入”，原生 CLI 配外部记忆就可能足够。两者都属于 training-free Agent 设计，取决于假设需要控制哪一层。

不能新建一个缺少正常上下文、工具和恢复机制的弱 Agent，再把补齐能力当主要效果。首先让基础版本达到合理完整度，再做同框架消融；另与成熟系统比较实际价值。

### 代码方向不应被 AGENTS.md 结果一票否决

静态预生成上下文文件、经历任务后积累的仓库事实、测试反馈驱动的 Agent 控制策略，是不同干预。此前“静态手册没有普遍收益，因此代码仓库不优先”的推理权重过大。

SWE-bench 本身支持不同 Agent 产生补丁。代码方向真正需要解决的是任务和机制证据、强原生基线、同仓库跨版本知识适用性及实验成本；不是“benchmark 只允许换模型”。本轮没有发现足够证据让它立即超过数据和 Web 的环境记忆候选，也不再因单项手册研究把它排除。

### 可改 Agent 也不保证符合环境知识主线

AppWorld 是明确的反例：它很好改，但把成功轨迹变成 Python helper，更可能是在学习操作 Skill；把官方文档缓存成提示，更多是文档访问优化。可以做这些 training-free 项目，只需准确命名，不能为了沿用 Memory 主线而混淆概念。

## 当前更合理的两个项目候选

### 数据环境中的跨任务事实学习与使用

具体研究对象是：执行任务后，Agent 怎样把亲自观察到的字段语义、关联或单位写入记忆；遇到新问题时，怎样利用这些事实决定先查什么、何时复核，以及哪些答案必须重新计算。

可以改变 Agent 的探索、写入和消费策略，模型与数据库保持相同。比较的结果包括新任务正确性、重复探索、误用旧知识和总费用。先用一个能独立判分的稳定环境检验，之后扩第二个环境；CL-Bench 只是入口，其单库规模、gold 反馈和评分限制不会因可改 Agent 而消失。

适合它的条件是：能在真实执行记录里找到同库不同任务反复确认相同事实的现象。若正常原生记忆或一份自动手册已足够，交付简单应用即可；不能靠故意隐藏必要文档来制造收益。

### Web 企业应用中的环境知识影响决策

具体研究对象是：Agent 从实际页面和动作反馈确认某个部署的字段、对象关系和操作前提，以后面对独立请求时利用这些事实选择下一步，并在状态冲突时重新观察。

可在 BrowserGym 和 AgentLab 的成熟环境接口上改主循环，研究记忆何时读取、怎样与当前页面共同进入决策，以及出现矛盾后如何恢复。环境、浏览器操作能力和模型相同，不给候选后台特权。

必须先区分：重复发现环境规律、同一次任务忘记目标、页面元素定位失败、动作没有生效。只有第一类直接支持当前主线；其他类即使值得做，也应改成对应的 Agent 策略项目。上一轮 LME 的单条循环轨迹没有证明它属于第一类，不能把它直接当 Memory 病例。

**两者目前都值得保留，不依据“能改 Agent”就宣布其中一个已有效。** 数据方向较容易隔离环境事实的作用；Web 方向提供更丰富的逐步决策改动空间。这是选型推断，不是实测排名。

## 下一轮实验应怎样换一个问法

旧问法容易变成：“哪个 benchmark 分数低，能不能加记忆？”

新问法是：“同一强模型在完成任务时，某项可观察的重复探索或错误决策，是否能被一个明确的 Agent 机制改善，并且优于现成简单办法？”

下一步应产出一张很具体的实验设计表：

|需要明确的内容|要求|
|---|---|
|现象|真实轨迹中发生的工作或错误；选例不外推发生率|
|可改的 Agent 部件|主循环、上下文、记忆写入或读取、验证或恢复，首轮只选择一个主要干预|
|机制假设|为什么这一干预可能改变后续行为；不能只说“更多上下文更好”|
|同框架比较|完整基础 Agent 与改动版用同模型、任务、权限和合理预算|
|现实对照|完整成熟 Agent、原生记忆、简单文档或手册、完整可用历史|
|成本|解题、整理、检索、核查、重试及额外角色全部记录，报告效果与实际总成本|
|留出与结果|新任务和模板隔离；正确率、配对退步、成本和行为变化分别报告|

例如可先比较自动形成的环境手册与按任务选择事实的记忆消费策略，而不是同时更换模型、Agent、工具、记忆库和评分器。若收益只来自增加思考轮数，应报告为更多推理预算的效果；若收益来自工具访问更广，应单独解释这项变化。

AppWorld 还明确规定 train 用于经验与示例、dev 用于调参和错误分析，test 仅用于最终测试；不能因为 training-free 就在 test 上反复观察错误再调提示。其他 benchmark 即使没有正式 dev 切分，我们也应划出不用于设计方法的任务。[开发限制](https://github.com/StonyBrookNLP/appworld#-agent-development-restrictions)

最终项目应能说明“改了 Agent 的哪一部分、解决哪个有证据的问题、在固定模型下改善了什么、代价是多少”。benchmark 是提供任务和判分的载体，不是项目的研究对象本身。
